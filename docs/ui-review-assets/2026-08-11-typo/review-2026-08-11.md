## 一、文字（6.2 字体 / 字号 / 字重 / 行高）

### 1.1 [严重] 没有字号体系，rem 小数漫天飞，产生大量非 2 倍数和低于 12px 的字号

指南 6.2.2 a)：**PC 端最小字号不小于 12px**；c)：**字号应为 2 的倍数**。5.5 节律要求尺寸规律一致。

实测根因（`base.css` + DOM）：

- `html` 根字号未设置，浏览器默认 **16px**，因此所有 `rem` 以 16 为基准。
- `base.css:84` 声明 `body { font-size: 15px }`，但 Naive UI `ConfigProvider` 把 body 计算值覆盖为 **14px**（实测 `bodyComputedFontSize=14px`），`base.css` 的 15px **实际是死代码**。
- 项目没有字号 token，每个组件各自挑 rem 小数。源码中出现过的 rem 值：0.68 / 0.7 / 0.72 / 0.75 / 0.78 / 0.8 / 0.82 / 0.84 / 0.85 / 0.88 / 0.9 / 0.92 / 0.94 / 0.95 / 0.96 / 0.97 / 0.98 / 1 / 1.1 / 1.2 / 1.3 / 1.35 / 1.5 / 1.6 / 1.75。

DOM 实测的违规样本（`getComputedStyle`，1920×1080 浅色）：

| 元素 | 文本 | 实测字号 | 违规 |
|---|---|---|---|
| `.n-tag.version-channel` | “测试版”（顶栏版本标） | **11.52px** | <12px ✗，非 2 倍数 ✗ |
| `.search-shortcut` | “Ctrl k” | **12.16px** | 非 2 倍数 ✗ |
| `.version-text` | “1.6.1-dev” | **13.12px** | 非 2 倍数 ✗ |
| `.sd-page-header h1`（共享页头） | 各页标题 | 24px | ✓ |
| `.page-head-copy h1`（base-setting） | “基本设置” | **25.6px** | 非 2 倍数 ✗ |
| `h1`（profile） | “性能分析” | 28px | ✓ |

依据文件：`ui/src/assets/base.css:84`；`ui/src/pages/misc/base-setting.vue:246`（1.6rem）；`ui/src/pages/misc/backup.vue:381`（1.6rem）；`ui/src/pages/tool/profile.vue:239`（1.75rem）；其余散落值见 grep（AppSearchMenu.vue:297/345/356/363/407、AppBreadcrumb.vue:152/158/164/211、AppSidebarBrand.vue:88/111/127、tool-test/* 等）。

整改建议：

1. 在 `:root` 固化根字号为 16px，并显式覆盖 Naive UI 的 body 字号，杜绝“16 / 15 / 14 三套基准并存”。
2. 建立有限字号 token，严格对齐指南示例并全部为 2 的倍数：标题 24 / 正文 14 / 辅助 12（紧凑专用），描述 13 可作为唯一例外。删除 0.68/0.7/0.72/0.78/0.82/0.84/0.85/0.92/0.95/0.97 等“间缝值”。
3. 任何小于 12px 的 UI 文本上抬到 12px（顶栏“测试版”“Ctrl k”等）。

### 1.2 [严重] 页面标题字号、字重、容器三套并存

指南 6.5.3、7.1、5.5：页面身份应稳定。DOM 实测：

| 页面 | h1 字号 | h1 字重 | 是否用共享 `PageHeader` |
|---|---|---|---|
| home / deck / backup / banlist / resource / helpdoc / js | 24px | **700** | ✓ `sd-page-header` |
| **misc/base-setting** | **25.6px** | **400** | ✗ 自定义 `.page-head` |
| **tool/profile** | **28px** | **400** | ✗ 自定义 |

- `PageHeader.vue:38-40` 定义共享标题为 24px / 700 / line-height 1.25，本身合规；问题在 base-setting 与 profile **未接入共享页头**。
- base-setting、profile 的 h1 字重为 **400（regular）**，比正文加粗还轻，页面层级被压平，违反 6.5.3 分组与信息层级要求（H1 应是页面最重文本）。
- 三种字号（24 / 25.6 / 28）中 25.6 又不是 2 倍数（见 1.1）。

整改：base-setting、profile 改用共享 `PageHeader`；确实需要差异化的页头动作，扩 `PageHeader` 的 slot，不要再开 `.page-head`。

### 1.3 [一般] `base.css` 声明的 CJK 字体栈被 Naive UI 覆盖，实际未生效

指南 6.2.1：优先用平台默认字体并保持一致。

- `base.css:76-83` 声明 `PingFang SC / Microsoft YaHei / 微软雅黑 / ...`。
- 实测 body 计算字体为 `v-sans, system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif, ...`（Naive UI 默认主题覆盖）。
- Windows 用户因系统 CJK 回退仍能正确显示雅黑，但 base.css 的声明是“看起来在管、实际没管”，团队无法靠编辑 base.css 调字体。

整改：统一在 Naive UI 的 `themeOverrides`（`common.fontFamily`）里集中声明字体栈，删除 base.css 中无效的 body 字体声明，避免两处不一致。

### 1.4 [轻微] 字重总体克制，符合 6.2.3

指南 6.2.3：正文加粗仅在强调时局部使用。实测正文多为 400，面包屑为 500（导航可接受），共享页头 700。字重本身**未见滥用**。唯一问题是 1.2 中页头反而过轻（400）。

### 1.5 [符合] 行高符合 6.2.2

指南 6.2.2 c)：行高为字号 1.5–1.6 倍。实测 body 14px / line-height 22.4px = 1.6 ✓；`PageHeader p` 1.5 ✓；`n-page-header` 14px / 21px = 1.5 ✓。文本块行高合规。控件内（按钮 12/12、标签 11.52/11.52）line-height=1 属行业惯例，不计违规。

### 1.6 [符合] 文字对比度全部达标

按指南表 1（T1/T2/T3）实测（WCAG 2.1 亮度公式，复合不透明度后）：

| token | @白底 | @页面底 #f3f4f6 | 指南目标 | 结论 |
|---|---|---|---|---|
| `--sd-text-primary` #111827 | 17.74 | 16.12 | T1 15:1 AAA | ✓ |
| `--sd-text-secondary` #4b5563 | 7.56 | 6.87 | T2 7:1 AAA | ✓（刚好） |
| `--sd-text-muted` rgba(31,41,55,.56) | 3.61 | 3.50 | T3 3.3:1 AA | ✓（刚好，仅用于描述） |

文字色彩**未见违规**。注意 `secondary` 与 `muted` 都贴着阈值，后续调整背景时需复核。

## 二、分割线（6.3）

### 2.1 [严重] 自定义分割线/容器边框 token 全面不满足 WCAG AA 3:1

指南 6.3：分割线与背景对比度应满足 **WCAG 2.1 AA**（非文本 UI 组件 1.4.11 = **3:1**）。实测（复合不透明度后取整 rgb）：

| token | 解析色 | @白底等效 | @页面底 #f3f4f6 | 比例 | 阈值 |
|---|---|---|---|---|---|
| `--sd-border` | rgba(17,24,39,.10) | rgb(231,232,233) | rgb(220,222,225) | **1.22–1.23 : 1** | ≥3:1 ✗ |
| `--sd-border-soft` | rgba(17,24,39,.08) | rgb(236,237,238) | rgb(225,226,229) | **1.17–1.18 : 1** | ≥3:1 ✗ |

即项目自定义的两条分隔线颜色，对比度只有标准的 **40%**，在浅色背景上几乎不可见。这两个 token 是自定义容器的**主分隔手段**，使用点包括：

- `PageHeader.vue:28` 页头下分割线（`--sd-border-soft`）
- `JsListView.vue:644,651` 列表面板外边框 / 头部分隔
- `QueryToolbar.vue:58` 查询区边框
- backup/resource 等卡片内部分隔

对比：Naive UI 自带控件边框（如 `n-input` 的 `rgb(224,224,230)` 实测 **15.97:1**）是合规的。结果就是**“Naive UI 原生控件边界清楚、项目自绘容器边界消失”**的割裂感，也削弱了卡片分组的可扫描性（违反 6.5.3 分组）。

整改：把 `--sd-border` 提到约 `rgba(17,24,39,.16)` 以上或直接用接近 `#d1d5db/#cbd5e1` 的实色，确保任意背景上 ≥3:1；`--sd-border-soft` 同步上调。深色侧 `rgba(148,163,184,.24)` 实测约 2:1，也偏低，建议提到 .34 以上。

## 三、图标（6.4）

### 3.1 [符合] 图标集统一

全站图标几乎全部为 **Element Plus（`i-ep-*`）经 `<n-icon>` 承载**（grep 命中 100+ 处，未发现混用其他图标体系）。满足 6.4 a)“风格一致”。NIcon 默认按字体尺寸居中渲染，6.4 e)“居中、留白”基本满足。

### 3.2 [轻微] 少量尺寸不统一，且存在填充/线性混用

- 显式尺寸散见 `size="14"`（ConditionBuilder）、`"18"`（DiffViewer）、`"20"`（FoldableCard）、`"22"`（ResourcePreview）、`"40"`（JsListView 空态）。数值都是 2 的倍数（6.4 d) ✓），但缺乏“行内=16 / 按钮=18 / 空态=40”这样的约定。
- `i-ep-box`、`i-ep-circle-plus-filled`、`i-ep-warning-filled`、`i-ep-document-checked` 等填充图标与默认线性图标混用，6.4 a) 风格一致性上有小瑕疵。

整改：约定 2–3 档图标尺寸 token；填充图标仅用于状态（成功/警告/错误），功能性图标统一线性。

## 四、布局（6.5 栅格 / 排版）

### 4.1 [严重] 没有统一的页级栅格/沟槽：8 个页面顶满 1704px，home 与 JS 却自限 1180px

指南 6.5.2：常用断点 1440/1200/768；6.5.3 排版应建立秩序感。实测（1920×1080，`sd-main-container` 宽，侧边栏 216px 后）：

| 页面 | 内容主体宽 | 现象 |
|---|---|---|
| deck / backup / banlist / resource / base-setting / profile / helpdoc | **1704px**（left 216 / right 0） | 顶满 |
| home（`index.vue:317 max-width:1180px`） | 自限 1180px 居中 | 两侧大片留白 |
| js（页面内列表容器） | 实测约 1180px（left 478 / right 262） | 自限 |

- 与上一轮审查对比：上一轮报告“默认页右侧空约 524px”在 deck/backup/banlist 等**已不复现**——它们现已铺满。这是正向变化。
- 但当前真正的问题是**没有页级统一基准线**：同是“综合设置”下的 backup/banlist/base-setting，backup 铺满 1704px、base-setting 也铺满，而 home 却自限 1180px；同为“扩展功能”的 deck 铺满、js 却自限 1180px。
- 铺满 1704px 对**表单/设置类**页面（base-setting）造成超长行与字段拉伸，损害可读性（6.5.3）；对表格/日志类（home 日志、banlist）铺满合理。

整改：

1. 由 `appShellLayout.ts` 统一管理 `default` 模式的 `max-width`（建议 1280–1440 区间），不要让每个页面各自 `max-width`。
2. home 的 `max-width:1180px`、JS 的内部限宽上提到统一容器；只保留 `wide`（编辑器/diff/复杂表格）铺满。
3. 形成两档而非“各页自定”。

### 4.2 [一般] default 与 wide 仅差一个类，缺乏文档化的取舍

`appShellLayout.ts:11-17`：`wide` 仅追加 `sd-main-container--wide`（width:100%, max-width:none），而 `default` 本身 `AppShell.vue:226` 也是 width:100%、无 max-width。即**default 与 wide 在宽度上当前实际等价**（都铺满），二者差异名存实亡——进一步说明 4.1 的“统一基准线”缺失。

## 五、组件（7.1 / 7.2）

### 5.1 [严重] 圆角没有 token，至少 11 档并存，JS 页形成独立视觉体系（仍存）

指南 5.5 节律、6.5.3 分组、7.1.10 卡片应可扫描、安静。源码与实测圆角：4 / 6 / 7 / 8 / 10 / 12 / 14 / 16 / 22 / 24 / 28 / 999px。

重灾区仍是上一轮指出的 **JS 页**，但位置从 `JsListView.vue`（已重构为 6px 朴素面板 ✓）上移到**页面壳 `pages/mod/js.vue`**：

```
pages/mod/js.vue:404  border-radius: 16px;
pages/mod/js.vue:406  linear-gradient(180deg, var(--sd-bg-elevated-tint) ...);
pages/mod/js.vue:407  box-shadow: ... (两段阴影)
```

- JS 页用“16px 圆角 + 渐变 + 双重阴影”的 hero 面板，内嵌 6px 朴素列表 → **同页之内**两套容器语言。
- 与 deck/backup/banlist/resource 的 Naive UI 朴素卡片（默认 3–6px、无渐变、无重阴影）对比，仍是截图中的风格割裂源。
- 其它大圆角/渐变/阴影集中在 about、tool-test、storyPainter，属于“展示型/沉浸型”页，可保留；但 JS 是**工具型管理页**，不应使用展示型语言。

整改：建立圆角 token（建议 `--sd-radius-sm 6 / md 8 / lg 12 / pill 999`），JS 页移除渐变与重阴影、改用与 deck 同款的朴素卡片 + 行展开/抽屉承载详情。

### 5.2 [严重] 备份页存在重复标题，卡片小标题层级被压平

- DOM：backup 页同时存在 h1“备份”、h2“备份设置”、且第一个 Tab 标签也叫“备份设置”（`backup.vue:18 tab="备份设置"` + `BackupConfigPanel` 内的 h2）。即 **Tab 名与内层 h2 文案重复**。
- backup 首个卡片小标题（h3）“自动备份”实测 **14px / 400**，与正文同号同重 → 卡片标题不具识别度，违反 6.5.3 分组与 7.1.10 卡片信息层级。

整改：Tab 改为不重复内层标题（如 Tab 用“设置 / 文件”，h1 用“备份”）；卡片小标题升到 15–16px / 600 或用 `n-card-header` 的标准标题样式。

### 5.3 [一般] 查询区已抽出 `QueryToolbar`，但默认值与各页调用仍不统一

- `QueryToolbar.vue` 已存在（正向），默认 `labelWidth=84`、`cols='1 s:2 l:3'`。
- 但调用方仍各自传不同 `label-width`（72/78/84/96）与 `cols`（l:3 / xl:3 / xl:5）。上一轮指出的“字段宽度与断点四套”**部分残留**。deck（`label-width=84, cols='1 s:2 l:3'`）是范本，应将 deck 的取值固化为 `QueryToolbar` 默认值，并删除其余页面的覆盖。

### 5.4 [符合] 主操作按钮基本遵循“每页一个突出样式”

抽查 deck：`重载牌堆`（primary，位于 `PageHeader`）+ `获取/上传牌堆`（info secondary，位于 `QueryToolbar` actions）。主次分明，符合 7.1.1 b)。其余抽查页未见多 primary 并列。

### 5.5 [符合] Naive UI 原生控件本体合规

n-input 边框 15.97:1、n-button 状态边框 3.13:1、tab 选中色 6.7:1，均 ≥ AA。7.1.4 文本输入占位、7.1.17 弹窗关闭/区分按钮、7.2.4 面包屑、7.2.5 分页等使用 Naive UI 标准形态，未见明显违规。

## 六、PC 端控件设计合理性与缺失

### 6.1 [合理] 导航框架（7.2.1）

左右布局（侧边栏 216px / 折叠 64px + 面包屑 + 内容），符合 7.2.1“功能多、层级多用左右布局”。侧边栏 `n-layout-sider`、`AppSidebar`、面包屑 `AppBreadcrumb`、全局搜索 `Ctrl+K`（`AppSearchMenu`）齐备。深/浅色切换、未保存提示抽屉、高级设置解锁均有承载。

### 6.2 [缺失] 缺少加载骨架/进度统一规范（7.1.16）

`n-spin` 散用，部分长列表（home 日志、backup 文件）直接空白到数据返回。指南 7.1.16：>2.5s 应显加载、<1s 不显。当前未见统一的 skeleton 或明确的 loading 节奏控制。

### 6.3 [缺失] 长表格未见“锁定首列/重要列”（7.1.11）

home 日志表在 1366×768 下水平空间紧张时，时间/级别/信息列未做粘性，信息列（长 URL）会挤压。指南 7.1.11：列多时重要信息列或操作列应始终可见。

### 6.4 [缺失] 标徽使用未规范（7.1.12）

顶栏同时出现版本标 `测试版`（11.52px，另见 1.1）与版本号文本，未统一为单一 `n-tag`/`n-badge`；指南 7.1.12：每个元素同时只应展示一个标徽。

### 6.5 [一般] 抽屉/弹窗宽度

`.the-dialog .n-card { width: min(760px, calc(100vw - 32px)) }`（base.css:148）统一了弹窗宽度，合理。但 `n-drawer` 默认宽度走 `getAppShellDrawerWidth() = min(320px, 86vw)`，仅移动端侧栏抽屉使用，未见业务抽屉滥用，OK。

## 七、优点小结（应保留）

1. **文字对比度全部达标**（T1/T2/T3），未见可读性硬伤。
2. **图标体系统一**（Element Plus + NIcon），风格一致。
3. **行高规范**（1.5–1.6），文本块阅读节奏正确。
4. **查询区已抽 `QueryToolbar`**、**列表已抽 `JsListView` 为 6px 朴素面板**——上一轮的“JS 卡片套卡片、查询区四套”已部分整改。
5. deck 页（共享 `PageHeader` + `QueryToolbar` + 朴素结果区 + 主操作入页头）是当前**最贴近指南的范本页**，建议作为其它页整改基线。
6. Naive UI 原生控件本体合规，弹窗宽度统一。
